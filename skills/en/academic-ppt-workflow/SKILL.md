# Academic Presentation Workflow

By default, use the following nine steps to produce professional academic presentations with a fresh, appealing design, reliable content, and a coherent narrative, in both image-based and editable formats. The user's scope, style, aspect ratio, and delivery requirements take precedence over defaults. Execute only the stages needed for the current task. Individual slides default to **16:9**; derive the overview canvas ratio from its grid.

**The core path for a new deck: use an image generation tool to design style thumbnails → review the full-deck layout → independently generate each slide using the selected thumbnail as a visual reference → review the image-based deck → faithfully reconstruct an editable deck → inspect every slide, correct issues, and verify delivery.** This is the skill's production method, not merely a list of files. Drawing complete slides with Pillow, SVG, HTML, or native PowerPoint objects and exporting them as PNGs does not replace the default image generation design process. Code may support precise content compositing, contact sheets, assembly, and reconstruction. See [Individual slide production](references/visual-production.md#individual-slide-production) for the division of responsibilities.

If the user explicitly requests purely native/code-based production or direct filling of an existing template, follow that method: complete the necessary content planning, build directly, assess the design against the template/user requirements, and perform the applicable Step 9 checks. Mark model generation and fidelity to an independent image reconstruction baseline as not applicable; do not invent an image-first reconstruction stage. A style reference image alone does not create this exception. For external reconstruction, local edits, and completed stages, use the entry points below without repeating work to meet a generation count. If image generation is unavailable, identify the unfinished design stage honestly; do not silently substitute programmatically drawn full slides and claim the workflow passed.

## Choose an entry point

| Task | Starting point and minimum preparation |
| --- | --- |
| Create a new deck | Step 1: establish the goal, materials, and requested endpoint |
| Continue a project from this workflow | Read existing content, style, baseline versions, and review records; resume the unfinished or affected stage. Verify the actual state if records are missing; do not fabricate history |
| Reconstruct external images/PPTs | Verify slide order, aspect ratio, clarity, text/data, and existing notes. Extract a minimal content record, register the input baseline and authorization, then perform Step 8 followed by Step 9. Do not rerun unrelated stages or require nonexistent historical files |
| Make local edits to an existing PPT | Identify the current version, target objects, and related components. After editing, use Step 9 to validate the affected scope without expanding it into a whole-deck redesign. If no original image baseline exists, follow the user requirements and existing style; do not claim original-image fidelity was verified |

Checking imported materials is a content and assembly review of the current input; it does not retroactively establish that historical Steps 7B/7C passed. Verify OCR against the original image. Check unclear numbers, missing data, and uncertain facts instead of guessing. A missing historical outline alone does not block reconstruction; seek clarification or state a limitation only when essential content cannot be determined.

Check the reading, generation, building, and rendering capabilities actually needed for the current stage. If `load_workspace_dependencies` is available, use it first to discover the document runtime. Before Steps 5–7 of a new deck, discover and use the image generation capability appropriate to the current environment. If an imagegen skill is available, read and follow it; do not conclude that generation is unavailable merely by checking local drawing libraries. Prefer the environment's current image generation tool. Where the tool supports explicit model selection, choose the latest suitable available capability. Record only verifiable tool/model details; do not guess the underlying version. If a capability is limited, continue independent work and explain the blocker. Do not mark unexecuted steps complete or switch to a separately paid API without authorization.

## Sources of authority and versions

| Record | Responsibility |
| --- | --- |
| Task constraints | The user sets scope, audience, style, duration, and required editability; keep these separate from factual evidence |
| Factual evidence | Original materials, source data, and verified sources. Resolve conflicts by recency, directness, credibility, and applicability; user-supplied sources are not automatically correct |
| Master content record | An outline or equivalent per-slide data containing approved wording, relationships, sources, and notes. For external reconstruction, derive it from the verified input |
| Style/structure preview | Thumbnails and presentation summaries used only for style selection and full-deck layout review |
| Visual baseline | Reviewed individual slide images or external input snapshots that have been confirmed or fall under applicable authorization, used for reconstruction comparison; preserve versions and paths |
| Final render copy | Images, PDFs, or an image-based PPT exported from the final editable PPT. These establish correspondence with the delivered version, but cannot replace an independent visual baseline as evidence of fidelity |

Keep established on-slide text, numbers, formulas, and labels accurate. Line breaks and layout whitespace may change. Before condensing, rewriting, adding, or removing body text, update and review the master content record. Graphics may express equivalent relationships; this does not authorize changing established wording or require mechanical duplication between text and graphics. Generated images and OCR are not new factual evidence.

Create records only when needed for the current stage; see [Minimum records](references/project-templates.md#minimum-records). Preserve original inputs. Use stable `slide_id` values and a separate display order for added or reordered slides. Filenames may vary, but artifact roles and version relationships must be clear.

## Confirmation and scope of changes

By default, request confirmation once after the image-based deck passes Step 7's internal review and before Step 8 reconstruction. If the user has explicitly requested full automation, no intermediate questions, or directly authorized starting/continuing reconstruction, record the relevant version and scope and continue. This also applies when the user supplies already accepted materials and asks for direct reconstruction. Authorization does not replace quality checks. Silence, or approval of only the outline/thumbnails, is not approval of the subsequently generated complete slide images.

Authorization to complete the editable version includes Step 9's detailed slide-by-slide review and necessary presentation fixes. Continue automatically after reconstruction without another routine approval. If the user requests review only, report issues without editing. If they request only the image-based version or another intermediate artifact, validate at that endpoint rather than starting reconstruction merely to complete all nine steps.

Only changes to meaning, content, or an accepted layout require updating the relevant content/visual baseline and handling the affected scope under the established interaction mode. Pure presentation fixes do not rerun upstream stages. Fill registered image placeholders according to their plan and validate them separately. Infer other parameters reasonably and record them without adding routine approvals. The user's specified endpoint always remains valid.

## Step 1 — Analyze requirements and materials

Establish the audience, goal, language, duration/slide count, required and excluded topics, style references, aspect ratio, delivery scope, and editing needs in a concise brief. Check which concepts, data, and conclusions the materials support, and list gaps. Enter Step 2 only for task-relevant gaps, source conflicts, currency checks, or a user request to search. If materials are sufficient, explain why and skip research. When internal data is missing, request necessary materials or limit the conclusions explicitly; do not fabricate information.

Distinguish explicit hard limits, approximate targets, and your own estimates. First plan the necessary, complete teaching units, then estimate slide count and duration. “Roughly 15–20 minutes” is not a reason to impose a 20-slide limit yourself. If an approximate target conflicts with necessary examples, section transitions, or closure, reasonably add slides or modestly exceed the estimate, explain why, and provide shortened/optional delivery routes. Do not artificially shorten speaking-time estimates to claim compliance. Explicit hard time/slide limits still apply: refine the wording or agree on scope tradeoffs. Completeness does not mean adding unrelated topics.

## Step 2 — Research as needed

Search for and read reliable sources addressing the gaps, prioritizing original evidence and checking dates and applicability. The research record captures findings, source locations, units/definitions, facts versus inferences, and unresolved questions. Stop expanding once the information supports the task. If research is skipped, do not create fictitious research records. For real-world incident case studies, read [Real-world incident cases](references/content-patterns.md#real-world-incident-cases) and plan report/news images and placeholders during outlining; do not wait until images are already available to trigger this requirement. The plan still applies when materials are sufficient and research is skipped. For other content, read the relevant sections of that reference according to purpose.

## Step 3 — Write a complete outline

Plan the full-deck narrative, section progression, and within-slide relationships before choosing layouts. A deck with multiple sections normally includes a cover, agenda, **a standalone title slide for each section**, the main content, a summary, and a closing slide. Here, sections correspond to the agenda's major parts; every second-level subheading does not need its own transition slide. Section slides display the section name and its question/scope to create a clear visual transition, rather than a blank page containing only a number. The summary reviews the content, the closing ends the main talk, and references have a separately planned location.

Follow explicit requests to omit or combine slides. Do not force sections into a very short, unsectioned deck. If a strict slide limit genuinely cannot accommodate supporting slides, record the tradeoff. Do not combine section slides merely because the talk is “15–20 minutes,” to reduce slide count, or for production convenience. A combined transition needs a visible section name, scope/transition cue, and hierarchy distinct from ordinary content. A corner section number, speaker note, or “section opener plus content” label alone does not establish a transition. Review both the original requirements and these default structures, not only an outline you have already shortened.

Use the [Per-slide content record](references/project-templates.md#per-slide-content-record) to write all on-slide text, informative annotations, data/formulas, graphical nodes, and the meanings of connections. Distinguish the title (what the slide covers), the central question (what it answers), and the takeaway (what the audience should remember); list the latter two separately only when appropriate. Definition/classification/mechanism slides generally suit topic- or question-based titles; results/argument slides may use evidence-backed conclusion titles. Respect the user's preferences. See [Content and speaker notes](references/content-patterns.md#content-and-speaker-notes) for their respective roles.

The master record must state each section's central question, scope, associated slides, and transitions from/to neighboring sections. Explain each slide's role and actual connection within its section, and whether its points are parallel, progressive, or subordinate. Group sections by the understanding task the audience must complete; merely combining several topics into a longer section name does not establish sound grouping. When the narrative moves from explaining a method to independent evaluation or response decisions, normally create a corresponding section. A brief validation or limitation that only explains the current method may remain within its section. Sections need not be equal in length or fixed in number. Records may be concise; repeated tables are unnecessary.

Plan where summaries, reflections, and outlooks belong and how they transition out of the main content. A concluding block spanning several slides normally appears in the agenda and has its own section slide. A single short summary may provide closure by itself, without an empty section slide. Do not let several unlisted concluding slides silently extend the final section.

Choose and read applicable entries in the [Pattern index](references/content-patterns.md#pattern-index). Plan slides as complete teaching units rather than equating every topic to one slide. When explaining abstract, multistep methods to nonexperts, include “principle + concrete example” by default; see [Methods and principles](references/content-patterns.md#methods-and-principles). A combined exercise cannot replace missing examples for individual methods. Use comparable title structures, terminology, and explanatory order within a topic group so that comparisons are possible; the entire deck need not share one title style or layout.

**Plan material completeness separately from live-delivery choices.** Expand each parallel topic promised by the agenda or overview using the same logical framework and comparable depth. If time is tight, prioritize adding core/optional slide routes, estimated timing, and skip transitions to the actual PPT speaker notes while retaining complete slides. Do not select one topic yourself and replace the remaining promised coverage with “this section focuses on…”. Follow an explicitly limited user scope and synchronize the agenda and overview. Background mentions do not require exhaustive treatment. For hard constraints such as strict slide limits, record a consistent compression plan; do not hide unmet requirements by dropping branches or rewriting the agenda.

## Step 4 — Review the outline

Use [Content and logic acceptance](references/quality-checks.md#content-and-logic-acceptance) to inspect the actual master record at the deck, section, and slide levels. Map agenda/overview promises to concrete teaching units; check the necessary information for applicable content patterns, section granularity, and placement of concluding content. Then read the titles and slide roles in sequence and verify the actual adjacent-slide transitions and notes. Review records may cite specific evidence in the master record; “logic passed” alone is insufficient. Also verify the case-study asset plan. Check factual correctness and clarity of explanation separately. Fix structural and logical gaps before starting visual production.

## Step 5 — Choose a style

Read [Thumbnails and style](references/visual-production.md#thumbnails-and-style). By default, **call an image generation tool** to create three style-thumbnail options, A/B/C, using the same slides, summaries, and order. Skip multiple options if there is already a definite template, selected style, or a request for only one option. A reference image alone does not cancel comparison. Actually inspect reference images and supply them as generation inputs. Explore meaningful composition or graphic-language differences within their constraints rather than recoloring one fixed layout.

Show the differences. If preferences are unclear, you may ask and use the waiting time for independent preparation. Allow a reasonable response opportunity under the current environment's interaction rules; do not immediately treat an option as chosen after presenting it. Wait if the user asks to choose first. Otherwise, you may select autonomously and explain your reasoning; add no wait if the user requests automatic completion. Establish the style and record colors, available fonts, grid, common titles/section numbers/dividers, and asset rules. Standardize shared parameters by slide role.

## Step 6 — Create thumbnails for the full deck

Reuse the selected option and generate previews for the remaining slides, covering all slides according to the current grid capacity and display order. Register batches, cells, and `slide_id` values. Derive summaries from the outline, retaining exact titles, main content, necessary qualifications, and graphical relationships; secondary explanations may be summarized. Before producing full slides, use [Thumbnail acceptance](references/quality-checks.md#thumbnail-acceptance) to check full-deck structure, section slides, design quality, and slide boundaries. Do not demand that every fine-print detail fit into small cells. Code may assemble fixed grids. An overview made after individual slides are complete cannot retroactively substitute for the earlier design preview.

## Step 7 — Produce the image-based version

- **7A Independently generate each slide:** Actually pass the full per-slide record, selected thumbnail, and corresponding cell to the image generation tool, generating a complete slide design individually. For applicable hybrid approaches, follow [Individual slide production](references/visual-production.md#individual-slide-production). Preserve the mapping between generation inputs and outputs. Merely supplying a style name, rerunning a fixed drawing function, or enlarging/cropping a thumbnail does not satisfy this step.
- **7B Check content and visuals:** Use [Individual slide acceptance](references/quality-checks.md#individual-slide-acceptance) to assess content correctness, visual design quality, and adherence to the production method separately; then check aspect ratio and cross-slide style. For overloaded slides, adjust the layout first. If content still does not fit, revise the outline or split the slide and synchronize related artifacts; do not shrink text indefinitely. Do not repeatedly modify slides that already pass.
- **7C Assemble:** Place one checked image per slide in display order in an image-based PPT with the same aspect ratio, add corresponding notes, and actually render it to verify assembly. Generate the review overview from these checked slides.
- **7D Confirm:** Following “Confirmation and scope of changes,” provide accessible image-based slides, previews, and any necessary placeholder explanations. Wait for explicit confirmation by default, or continue under applicable existing authorization. Record the status and relevant version.

## Step 8 — Editable reconstruction, complete initial review, and correction

Verify the current visual baseline, content record, input checks, and applicable authorization. For external imports, use the entry-point checks without demanding historical workflow files. Follow [Editable reconstruction](references/visual-production.md#editable-reconstruction) to decompose and measure elements, choose object types, and build each slide. Aim for faithful reconstruction. Do not simplify icons or change layouts merely for construction convenience, or disguise a full-slide screenshot plus transparent text as editable content. Verify the target editing software and required editing capabilities. Judge complexity per element; validate applicable complex styles, formulas, or mixed components before reusing them in bulk. Assess retained bitmaps, alternative implementations, and approximations under [Reconstruction alternatives and fidelity loss](references/quality-checks.md#reconstruction-alternatives-and-fidelity-loss); do not defer avoidable simplifications to the second review.

Review while building. After reconstruction, read and execute the entire [Reconstruction and fidelity acceptance](references/quality-checks.md#reconstruction-and-fidelity-acceptance) section: file/editing capability, elements/relationships, actual render comparison, and the slide-by-slide method are all required. Perform a complete initial review of every slide in scope, log issues, correct them in editable objects, rerender affected slides, and check for regressions. Structural checks alone are insufficient; do not leave known, fixable issues for Step 9. After the initial review passes, save the corrected version and per-slide evidence, then continue to Step 9. A successful build or initial pass is not final delivery. If the baseline contains a factual error, verify it and update the content and affected baseline first. Do not copy known errors or secretly replace the baseline merely to pass comparison.

## Step 9 — Detailed slide-by-slide review, correction, and delivery acceptance

In a reconstruction task, this is a second complete review of the corrected version from Step 8. Read and execute the entire [Reconstruction and fidelity acceptance](references/quality-checks.md#reconstruction-and-fidelity-acceptance) section again, organizing the review according to its [Detailed slide-by-slide review procedure](references/quality-checks.md#detailed-slide-by-slide-review-procedure). Do not merely check whether previously found issues were fixed: reinspect every applicable slide to find initial-review omissions and problems introduced by fixes. Whole-deck delivery covers every slide. Local tasks remain limited to the authorized scope and related effects. Neither another agent nor a new user approval is required. Use the same records while retaining each round's input version, findings, fixes, and conclusions separately:

- **9A Verify the corrected version and renders:** Identify the current input version, which should be the initially corrected version for reconstruction tasks. Record the source PPT version/hash, tool, and actual font environment. Reuse existing renders only if they match the current version and applicable environment; otherwise export individual slide images and an overview from the current PPT. Original images or old screenshots are not substitutes. Reusing renders does not mean carrying over the first review's “pass”; actually inspect every slide again.
- **9B Find issues slide by slide:** First inspect every slide in scope and save a list before making changes. Check full-slide layout and relationships, then zoom in on text, borders, arrows, icons, and crops, and check consistency across slides/topic groups. Judge fidelity and final readability separately; neither an overview alone nor representative sampling is sufficient. Also use [Reconstruction alternatives and fidelity loss](references/quality-checks.md#reconstruction-alternatives-and-fidelity-loss) to compare actual objects and reassess bitmaps, substitutes, and approximations retained during the first review. No typos or overlaps, or an existing “fidelity limits” note, does not establish that these items pass.
- **9C Correct and recheck:** Fix editable objects and trace issues to similar components and processing methods. Rerender affected slides and review the original issue, neighboring elements, and content/notes. Within this round, evidence may be reused for slides already inspected whose versions have not changed and which are unaffected by shared changes. This does not permit skipping the second slide-by-slide review. Do not impose a fixed number of correction cycles.
- **9D Verify delivery:** Confirm per-slide coverage, issue resolution, and current rendering evidence. Check the final files' editability, notes, slide order, and version consistency across the delivered PPT, previews, records, and other copies. Resolve obvious, fixable issues before final delivery. State unverified or capability-limited parts honestly; do not call a candidate draft an accepted final product.

## Delivery and iteration

[Correction and completion criteria](references/quality-checks.md#correction-and-completion-criteria) apply across all stages. Content changes update the master record and relevant derived artifacts; recheck the semantics of affected sections and transitions to neighboring slides. Presentation adjustments update the relevant objects; changes to shared components require checking all slides that use them. Deliver only artifacts within the current scope and report their actual status. By default, the complete workflow delivers both PPT versions, content/style and review records, actual research records if any, all thumbnails and individual slide images, previews, necessary assets, and reproducible build code. Lead the final response with deliverable links and state the slide count, acceptance status, elements still retained as images, and unresolved limitations.
